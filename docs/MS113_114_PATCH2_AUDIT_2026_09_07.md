# MS-113/114 및 patch-2 독립 감사 — 2026-09-07

## 결론

현재 가장 강한 결과는 “새 지역의 적은 dense mask로도 frozen OlmoEarth cache 위 작은 head를
효율적으로 적응할 수 있다”이다. 그러나 **“라벨 5장이면 끝이고 그 이상은 낭비”는 아직 증명되지
않았다.** MS-114의 R/T/P/N 방법 가지는 등록 kill-gate에 따라 닫는다. 다음 유효 실험은 라벨을 더
영리하게 쓰는 방법이 아니라, 동일 관측을 더 조밀한 token grid로 읽는 것이 실제 경계 정보를
보존하는지 분해하는 4-arm cache-contract 실험이다.

## 1. MS-113에서 살아 있는 것과 과장된 것

| 판정 | 문장 | 근거 |
|---|---|---|
| 유지 | Sen12에서 K=5 A1 macro `.294`와 pool A1 `.299`의 **aggregate gap이 작았다** | MS-113 |
| 유지 | Solar도 K=5 `.582`, pool `.609`로 큰 폭의 평균 headroom은 관측되지 않았다 | MS-113 |
| 유지 | 현 decoder에서 method kill-gate(격차 ≥`.05`, 6/8)는 실패했다 | 사전 등록 규칙 |
| 철회 | “5장에서 포화했다” | K=20 `.317`이 pool `.299`보다 높아 단조 learning curve가 아님 |
| 철회 | “그 이상 라벨 수집은 낭비” | support draw·양성량·update 수·threshold 계약이 다름 |
| 금지 | “라벨 5개” | 한 sample은 128×128 pixel dense mask이고 지역별 positive incidence가 9–65% |

MS-113의 `A1_pool`은 엄밀한 상한이 아니다. 고정된 head, 최대 6,000 update, 한 support
구성의 결과다. 더 많은 데이터에서 성능이 낮아질 수 있다는 사실은 “포화”뿐 아니라 class imbalance,
optimization, support composition 또는 threshold noise로도 설명된다. 특히 기존 FP-matched IoU의
작동점은 target query의 빈 타일 라벨을 사용하므로 **과학적 비교 지표일 수는 있어도 deployable
decision metric은 아니다.**

새 계약은 `config/label_efficiency_curve_prereg_v0.json`이다. K=`0/1/2/5/10/20/50/all`을 동일
무작위 공간-block permutation의 prefix로 만들고, 5 draw, fixed-update를 primary로 둔다. tie-correct
AP와 source-validation/support-only threshold IoU가 함께 `ε=.02` 안에 들 때만 saturation이라 부른다.

## 2. MS-114는 왜 더 진행하지 않는가

R(검색 재가중), T(장 통계 보정), P(자기학습), N(kNN)은 어느 것도 등록된 “A1 대비 +`.03`, 두
개발 지역”을 통과하지 못했다. Solar의 최악 fold와 AP 개선은 **평균 정확도 방법**이 아니라
guardrail 후보로만 남긴다. 이 결과를 이름만 바꿔 method track으로 되살리지 않는다.

이 실패는 중요한 진단을 준다. 현재 병목은 support label 활용 알고리즘보다 cache가 보존한 공간
정보일 가능성이 크다. 단, 이는 patch-2 결과 전까지 가설이다.

## 3. patch-2 실행 감사에서 발견한 결함

decoder metric이 한 건도 나오기 전에 첫 실행을 중단했다. 발견한 결함은 두 개다.

1. 추출기는 patch-2에서 `(768,64,64)`를 만들지만 validator는 `(768,32,32)`를 hard-code했다.
   partial cache 1,517개는 실제 shape가 정상이어도 모두 invalid로 판정되어 재계산될 수 있었다.
2. `resolution_chain.sh`가 `set -e` 없이 extraction return code만 기록하고 계속 진행했다. 즉 cache
   audit가 실패해도 decoder 결과를 만들 수 있었다.

수정 후 계약은 shape를 `128/patch`에서 계산하고, 전수 ID/shape/dtype audit가
`all_gates_pass=true`가 아니면 decoder를 시작하지 않는다. runner는 GPU1 빈 상태, non-blocking lock,
새 OUTROOT, pre-run code snapshot, SHA-256, completion count를 모두 강제한다. partial cache는
수정 validator가 읽기·shape를 통과한 파일만 재사용한다.

## 4. “20 m token”이 의미하는 것

OlmoEarth v1의 설치 소스는 `min_patch_size=1`, `max_patch_size=8`인 FlexiViT 계열 경로를 가지며,
요청 patch가 base patch와 다르면 입력을 내부 보간한 뒤 base projection을 적용한다. 따라서
patch-2는 센서의 새 10 m 측정을 생성하지 않는다.

정확한 질문은 다음이다.

> 같은 Sentinel 관측에서 FlexiViT의 더 조밀한 tokenization이 frozen cache의 작은-object/boundary
> utility를 올리며, 그 이득이 decoder grid나 단순 보간으로 설명되지 않는가?

이는 FlexiViT의 patch-size compute/accuracy trade-off, Scale-MAE와 AnySat의 scale-aware EO 흐름과
맞지만, 우리 기여는 새 backbone이 아니다. **materialized cache의 token resolution × storage ×
reuse utility 계약을 측정하는 것**이다.

## 5. 4-arm 원인 분리

| arm | cache/readout | 무엇을 분리하나 |
|---|---|---|
| P4_NATIVE | 32×32, 봉인 3-seed 기준 | 등록 promotion 기준 |
| P4_NATIVE_CONTROL | 32×32, 새 trainer seed 1 | 새 3개 arm과 같은 trainer 보정(봉인 기준 ±.03) |
| P4_UPSAMPLE2 | P4 token을 64×64로 bilinear 확대 | decoder가 큰 grid를 받은 효과만 |
| P2_NATIVE | Flexi patch-2의 64×64 token | 등록 개입 |
| P2_AVGPOOL2 | P2를 2×2 평균해 32×32 | P2의 fine-grid 정보를 제거 |

기존 v1c gate는 바꾸지 않는다: P2_NATIVE−P4_NATIVE ≥`.03`이고 6/8 지역 승리. 원인 주장에는
추가로 같은 trainer의 P4_NATIVE_CONTROL이 봉인 기준 ±`.03` 안이고, P2_NATIVE가
P4_UPSAMPLE2와 P2_AVGPOOL2를 모두 이겨야 한다. P4_UPSAMPLE2가 같은 이득을 내면 decoder-grid
artifact이고, P2_AVGPOOL2가 유지하면 fine boundary 설명은 기각한다.

주의: Sen12 8지역은 이미 여러 번 열어본 개발 세트다. 여기서 8/8이 나와도 confirmatory라고 부르지
않는다. 통과 시 seed 2·3과 실제 cache byte/extraction/train/inference cost를 채운 뒤, 독립 외부
과업 또는 Korea sealed holdout에서 한 번 확인한다.

## 6. Korea shared-cache 3-task가 중요한 이유

한국 3-task는 단순 응용 demo가 아니라 현재 두 모호성을 동시에 분리할 수 있다.

| shared cube task | 예상 공간 수요 | 묻는 질문 |
|---|---|---|
| land cover | 넓고 연속적인 영역 | patch-4로도 충분한가 |
| deforestation | 시간 변화 + 중간 크기 경계 | dense token이 변화 경계를 보존하는가 |
| landslide | 작고 불규칙한 경계 | patch-2 비용이 실제 utility로 회수되는가 |

같은 12-band cube를 공유하므로 cache 비용은 한 번, task head는 세 개다. 따라서 주표는
`task × patch(4/2) × action(A0/A1)`과 실제 **N-task amortized cost**가 된다. 가장 유의미한 결과는
“항상 patch-2”가 아니라, coarse task는 저렴한 patch-4를 재사용하고 fine-boundary task만 patch-2를
materialize하는 결정 규칙이다. 이것이 성공하면 캐시 계약 설계가 방법 기여로 올라간다.

그러나 Korea label은 현재 amendment의 transient-error 6건과 selection-bias gate를 닫고, 이
factorial과 판정 기준을 별도 addendum으로 commit하기 전까지 개봉하지 않는다.

## 7. 실행 순서

1. 수정 코드 unit/syntax/JSON 검사.
2. 서버에 snapshot 대상 코드를 push.
3. GPU1이 비었을 때만 `resolution_chain.sh` 시작. 현재 다른 작업이 GPU1을 점유하므로 강제 실행 금지.
4. cache 전수 audit 후 P4_NATIVE_CONTROL → P4_UPSAMPLE2 → P2_NATIVE → P2_AVGPOOL2, seed 1.
5. `verify_resolution_contract.py`가 등록 gate와 세 mechanism delta를 원시 JSON에서 재계산.
6. 통과할 때만 seed 2·3. 실패하면 patch-size 방법을 닫고 DEN/Korea action matrix로 복귀.

## CVPR 판정

patch-2 하나가 좋아지는 것만으로는 CVPR method novelty가 아니다. FlexiViT/THOR/AnySat이 이미
가변 patch·scale-aware representation을 점유한다. CVPR급으로 올라가는 조건은 다음 묶음이다.

1. 두 task의 cache-first/few-shot 결과,
2. label-efficiency를 deployable metric과 nested curve로 정리,
3. token resolution–storage–multi-task utility의 원인 분리,
4. 처음 보는 Korea task에서 비용 제약 action rule의 낮은 regret.

즉 헤드라인은 “patch를 줄이면 좋아진다”가 아니라 **“공유 Earth embedding cache를 어떤 해상도로
materialize하고 언제 head만 적응해야 하는지를 task scale·label mass·비용으로 결정한다”**여야 한다.
